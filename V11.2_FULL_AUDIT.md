# AIHACKBins v11.2 — full-source technical audit

**Basis:** uploaded `AIHACKBins-v11.2-evidence-filter-nav-llm04.zip`, audited offline. No real AI targets executed and local Chromium browser navigation was blocked by administrator policy.

## Inventory

- **32** OWASP AI Testing Guide objectives in the Baseline, but **21** have directly linked RC records.
- **35** distinct primary source URLs. Top two URLs are reused for **13** and **10** records, respectively. This is an attribution-review signal, not automatic evidence of incorrect citations.
- **57** ATLAS-mapped records, **10** distinct ID strings.
- Input type distribution: text=54, generator=2, file=6, workflow=4, json=1, dataset=1.
- Two project tracks: Hacking AI systems=66, Hacking with AI=2.

## Critical defects found

1. **CI failure:** `scripts/validate_release.py` fails at RC-266 (and RC-267/268) because required OWASP methodology fields are missing. `scripts/validate_mapping_policy.py` also hardcodes 65 records. The GitHub workflow runs `validate_release.py`, so CI can fail even when `validate.py` passes.
2. **Stale audit metadata:** `data/audit.json` currently reports `authored_illustration_pairs: 65`, but there are 68 outcome records. The original edition/source metadata still describes earlier releases.
3. **Cloudflare packaging:** the uploaded ZIP put the site inside a `v111-review/` folder. Direct-upload ZIPs should have `index.html` at archive root. The fixed-navigation ZIP corrects the package layout.
4. **Framework semantic review:** new RC-266/267/268 contain mappings that pass syntactic validation but have not been independently compared against current MITRE ATLAS / OWASP official technique definitions. AITG coverage must not be equated with verified vulnerabilities.
5. **Input semantics:** RC-266 and RC-267 are `file` entries with downloadable fixtures but the primary `payload` is a written procedure; RC-268 is a long-term research workflow. Show a file download or procedure action as primary, not a misleading standalone prompt.

## Usability by assessment target

**Chatbot:** strongest for direct prompting, encoded inputs, role confusion, multilingual variations and prompt leakage. A practical pentest needs a clear test target, protected task/secret canary, model version, repeated clean-vs-injected comparisons, and confirmation of real impact.

**AI application:** strongest for indirect injection through documents, web pages, email, JSON, OCR, metadata and RAG. It needs better trust-boundary diagrams, ingestion confirmation and controlled tenant/authorisation tests.

**AI agent / MCP:** strongest for tool-description injection, agent skill files, memory and cross-tool behaviour. It needs actual (or clearly simulated) tool-call traces and separation of model intent from executed action and independent tool authorisation.

**Broader ML:** model theft, membership inference and poisoning require specialist research contexts and evidence, so lab narratives must show measurements, not one-off success markers.
